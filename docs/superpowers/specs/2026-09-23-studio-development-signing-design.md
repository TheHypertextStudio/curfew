# Hypertext Studio development signing design

## Purpose and acceptance boundary

The installed Curfew development app is signed by the personal Apple team and its provisioning profile does not grant Associated Domains. Xcode is signed in to the Hypertext Studio LLC team (`T95VDD3A4W`), but Apple reports the existing `studio.hypertext.curfew` and `studio.hypertext.curfew.dev` App IDs unavailable to that team. Re-signing the existing development identity would also reuse local data and helper registrations. A company-signed build therefore needs a distinct identity before it can safely test the claimed HTTPS account callback on this Mac.

This design is a staging verification vehicle, not a substitute for the requested remote MCP product. Acceptance still requires a signed macOS callback, fresh passkey/Apple account enrollment through Recovery Key acknowledgement, and a real Claude-on-phone request that locks and unlocks this Mac. Unsigned tests, deployed AASA, and an OAuth redirect alone do not count.

## Selected approach

Add a third `CurfewFlavor.studioDevelopment` and an Xcode `StudioDev` configuration. Keep existing personal-team Debug and Release identities byte-for-byte unchanged. The company build uses app ID `studio.hypertext.curfew.studio.dev`, widget ID `studio.hypertext.curfew.studio.dev.widget`, and App Group `group.studio.hypertext.curfew.studio.dev`; its staging account callback uses only `curfew-account-staging.hypertext.studio`. Its visible name is `Curfew (Studio Dev)`. The built wrapper must be named `Curfew Studio Dev.app` (not merely have a different `CFBundleDisplayName`) and must install at exactly `/Applications/Curfew Studio Dev.app`; verify the wrapper and destination before copying so neither existing `Curfew.app` can be replaced.

An alternative of changing the Debug signing team is rejected because the existing App IDs are unavailable to the company team and because that would share preferences, Keychain service names, daemon state, and browser registrations. A standalone callback probe could test provisioning sooner, but it would not prove the real app's enrollment and remote-command path. It is optional as a diagnostic, not an acceptance endpoint.

## Identity and state isolation

`studioDevelopment` resolves before the existing `.dev` bundle-segment fallback, including the widget ID. It is propagated to app-launched `curfew-ctl`, `curfew-mcp`, the native browser host, and `curfew-daemon` as `CURFEW_FLAVOR=studioDevelopment`; a manually invoked CLI must receive that environment value explicitly. The third flavor derives unique values for the app bundle, UserDefaults suite, user and privileged Application Support, App Group, MCP queue and socket, widget kind, native-host manifest, audit logs, daemon plist/label, and Claude Desktop server key (`curfew-studio-dev`). Production and personal development values do not change. StudioDev enforcement priority is lower than personal development, which remains lower than production.

The app's enforcement-owner check is not sufficient for the root daemon. The StudioDev daemon must read and validate the shared ownership record before any destructive action, and stand down while a live higher-priority owner enforces, even if StudioDev has its own deadline and its app heartbeat is stale. Its remote-command backend rejects a new lock with the existing `rejected/ineligible` result when a higher-priority owner is live; it must not report `applied` for a lock it cannot enforce. It may continue reporting previously resolved receipts. For this side-by-side staging vehicle, the StudioDev daemon never invokes `/sbin/shutdown` and never invokes the global `pkill -x shutdown` cancellation path. This is an intentional test-build limitation; it does not remove lock/unlock commands, app overlays, daemon command verification, or receipts. Existing production and personal-development daemon behavior stays unchanged. A separate process-owned shutdown cancellation design is required before a future company production build enables root shutdown.

The Curfew account, Docket OAuth, and legacy coordinator assertion Keychain services must not share service names with the other flavors. StudioDev uses the same staging network origins as personal Debug but distinct local secrets. No automatic Keychain migration or settings copy occurs. Uninstall is confined to its own data, preferences, App Group, browser manifest, and Keychain services; it must never remove either existing app's data or registrations. Settings' post-uninstall Finder action must reveal `/Applications/Curfew Studio Dev.app`, never `/Applications/Curfew.app`. The production `scripts/uninstall.sh` is not a StudioDev uninstall path and must not be invoked for this flavor.

The Docket private-use callback scheme in `Info.plist`, its authorization request, callback validator, and dynamic-client registration must use one flavor-specific value. StudioDev uses `studio.hypertext.curfew.studio.dev`; the two existing builds retain `studio.hypertext.curfew`. The Curfew account flow remains the claimed HTTPS callback, never this private-use scheme.

The existing unpacked Chrome development extension talks to the personal development native-host name. StudioDev must not claim that extension as its own or silently send browser policy to the personal host. Until a separately keyed StudioDev extension exists, the StudioDev app leaves its browser-native runtime inactive and explains that this staging build cannot exercise Chrome task-browser enforcement. This exception does not disable account enrollment, local MCP, or the privileged remote-command path.

## Build, signing, and account service

`StudioDev` inherits Debug compilation behavior and `CURFEW_STAGING`, while the helper bundling script explicitly accepts its daemon plist and staging flag. Its Xcode wrapper name is distinct without changing the Swift `Curfew` module or the executable name; test-host paths must follow the computed wrapper. The app and widget use Hypertext Studio team `T95VDD3A4W`; the main app's entitlements contain the unique App Group and only staging `applinks` and `webcredentials` domains. The widget uses the same unique App Group. No production Associated Domain is claimed by this staging build. All app targets remain on `0.0.x`; no package version or protocol shape changes are needed.

The coordinator must list the exact `T95VDD3A4W.studio.hypertext.curfew.studio.dev` app ID in staging AASA and the official-native-client allowlist before testing. The widget needs a matching team-owned App ID and profile. A profile or signed binary that lacks the App Group or Associated Domains entitlements fails the gate even if Xcode reports BUILD SUCCEEDED. Do not delete or transfer personal-team App IDs as part of this work.

## Failure handling and user-facing behavior

If provisioning is unavailable, the signed build fails rather than falling back to ad-hoc signing or a personal team. If AASA or the claimed callback is not delivered, Settings shows a cancellable/retryable sign-in path without claiming the passkey failed. If enrollment cannot read a retained checkpoint, the already implemented `storageUnavailable` state blocks replacement sign-in and preserves the checkpoint. When a higher-priority Curfew is enforcing, both StudioDev's app and daemon yield rather than changing the other app's lockout. Because its bundle ID is new, StudioDev needs its own macOS Accessibility permission; the personal app's existing grant does not transfer.

The StudioDev build is labeled in the app and in its install path so a user can tell it is a staging test. Account copy remains the same layperson wording used in Debug. The browser-enforcement exception must be visible only where that integration is offered, not as a warning on unrelated account screens.

## Verification and release gate

First, add failing tests for third-flavor resolution and a literal noncollision matrix across all three flavors, including Keychain services, Docket callback schemes, daemon label/path, browser host, and Claude Desktop key. Add daemon tests for a live higher-priority owner with a stale StudioDev heartbeat, and for StudioDev issuing no root shutdown or global shutdown cancellation when both flavor daemons have pending work. Add an uninstall-target test/dry-run covering every StudioDev file, preference, Keychain, and registration target plus the post-uninstall Finder destination; assert no personal/production target appears. Then implement the flavor and build settings, update `Documentation/todos.md` and `Documentation/todo-test-matrix.md`, run focused tests, SwiftFormat, SwiftLint, all Curfew unit tests, and an unsigned `StudioDev` build. Verify the built wrapper filename, app/widget `Info.plist`, and effective entitlements. Do not install until this local gate passes.

Next, register the team-owned IDs and App Group under the Hypertext Studio account, create/refresh provisioning, deploy the exact coordinator native-client/AASA identity, and produce a signed `StudioDev` build. Verify team IDs and entitlements with `codesign` and provisioning inspection, plus the live AASA response. Verify the source bundle basename is `Curfew Studio Dev.app`, the destination is exactly `/Applications/Curfew Studio Dev.app`, and `/Applications/Curfew.app` is not the copy target. Install side by side only after recording the personal app's bundle, settings, Keychain identities, and daemon state for before/after comparison. Exercise the claimed HTTPS callback and complete account enrollment from a fresh account. With personal development stopped, trace the authenticated phone MCP tool call and scope through coordinator-signed command delivery, StudioDev daemon verification/receipt, and the visible Mac lock and unlock; separately prove both StudioDev app and daemon yield to a running higher-priority app, including a stale StudioDev heartbeat. Confirm the personal install remains unchanged and record observable results and failures in the PR. A build or CI pass is not a substitute for these runtime checks.

Rollback removes only the StudioDev installation and its own registrations/state through the flavor-aware app flow. Never use the production uninstall script for StudioDev. The existing personal build stays installed and untouched. Do not merge this as a production signing migration; company production identity and data migration require a separate, explicitly tested release design.
